# Demo authentication (Step 6.1)

This is a fictional-data portfolio demo with one shared demo account. It is not a production healthcare authentication system. No regulatory compliance is claimed. Registration, patient accounts, roles, external identity providers and deployment are outside this milestone.

## Architecture and API

The Flask factory installs `app/auth.py` after registering existing blueprints. A single `before_request` hook protects every registered `/api/` operation except health, login and session bootstrap. Unknown routes retain their 404 responses. `TESTING` never disables protection. No database tables or migrations were added.

Flask signs the session cookie with an environment-provided secret. The cookie contains only a demo ID, an absolute expiration, a random CSRF token, and a keyed credential-version digest. Cookies are signed, not encrypted: passwords and password hashes never enter the cookie. Changing the configured username/hash invalidates existing sessions. API responses use `Cache-Control: no-store`.

| Endpoint                | Behavior                                                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/health`       | Public; existing payload unchanged.                                                                                                        |
| `GET /api/auth/me`      | 200 with `{user, csrf_token, expires_at}` for a valid session; 401 with a fresh anonymous `csrf_token` for login bootstrap.                |
| `POST /api/auth/login`  | JSON `{username,password}` plus `X-CSRF-Token`; verifies Werkzeug hash, clears previous state, rotates CSRF, returns the session metadata. |
| `POST /api/auth/logout` | Authenticated POST with CSRF; clears the current cookie and returns `{message:"Signed out."}`.                                             |

User metadata is `{id:"demo",display_name:"Demo User"}`. Invalid credentials receive the same generic 401 for either incorrect field. Malformed login values receive 400, missing/expired sessions receive 401, CSRF failures receive 403, and absent/invalid auth configuration receives sanitized 503. Passwords are limited to 1–1024 Unicode characters and usernames to 1–100; login JSON is limited to 16 KiB. New credentials generated by the helper require at least 12 characters.

Dashboard, support requests, document metadata/upload/delete/search, and AI requests require a session. Existing successful request/response contracts, including `POST /api/ai/ask` with `{question}` and `{answer,sources,grounded}`, are unchanged. PDF storage remains private with no public download route. PDF worker imports remain independent of the web/auth stack.

## Local credential setup

Required environment variables:

| Variable                | Requirement                                                                                           |
| ----------------------- | ----------------------------------------------------------------------------------------------------- |
| `DEMO_USERNAME`         | One fictional username; no default.                                                                   |
| `DEMO_PASSWORD_HASH`    | Werkzeug `scrypt:32768:8:1` hash, or `pbkdf2:sha256:600000` / `pbkdf2:sha256:1000000`; no plaintext.  |
| `SECRET_KEY`            | Unique cryptographically random secret, at least 32 characters; no placeholder/default/fallback.      |
| `SESSION_COOKIE_SECURE` | Defaults to `true`. Explicitly set `false` only for local HTTP development. Always `true` over HTTPS. |

The existing database settings are still required for normal app startup. `backend/.env` was not edited. The example file contains empty auth variables. In an interactive PowerShell terminal, from the project root:

```powershell
.\backend\.venv\Scripts\python.exe backend/scripts/generate_demo_auth.py
```

The helper uses hidden password prompts, confirmation, Werkzeug scrypt and a random signing key. It writes `backend/instance/demo-auth.json` only if absent and prints no password, hash or signing secret. The directory is Git ignored. Keep its Windows folder ACL restricted to your account; POSIX mode bits alone do not enforce Windows ACLs. Do not paste this file into chat, logs, screenshots or artifacts.

Load those values into the backend process without printing them or changing `.env`:

```powershell
$demoAuth = Get-Content -Raw -LiteralPath backend/instance/demo-auth.json | ConvertFrom-Json
$env:DEMO_USERNAME = $demoAuth.DEMO_USERNAME
$env:DEMO_PASSWORD_HASH = $demoAuth.DEMO_PASSWORD_HASH
$env:SECRET_KEY = $demoAuth.SECRET_KEY
$env:SESSION_COOKIE_SECURE = 'false'
$env:FLASK_PORT = '5053'
.\backend\.venv\Scripts\python.exe backend/run.py
```

In another terminal run `npm.cmd run dev` from `frontend/`. Keep `VITE_API_BASE_URL` empty so the browser uses `/api` through Vite's existing proxy to `127.0.0.1:5053`. Use the same hostname consistently. Stop the process and clear process environment variables when finished. Rotate manually using a newly generated password/hash/key; the helper deliberately refuses to overwrite existing configuration. Reviewers should receive unique demo-only credentials through a private channel, never in the frontend bundle or a public README. Do not reuse a production credential.

## Session, origin and CSRF controls

The cookie is HttpOnly, SameSite=Lax, host-only, scoped to `/api`, and Secure by default. The session lasts eight hours from login; reads do not extend it. Flask's signed-cookie timestamp and the stored absolute expiration are both checked. The React layer restores `/auth/me` before rendering protected content and uses the server expiration for a local timeout. Private 401 responses clear auth, abort in-flight requests, remove private query/mutation cache data, unmount the local AI conversation, and return to login. A 403 does not expire authentication. Failed mutations are never automatically retried.

The anonymous `/auth/me` response creates the synchronizer CSRF token needed for login. Login rotates it. All unsafe API methods require the cookie-bound `X-CSRF-Token`, including support mutations, multipart document uploads, document deletion, AI POSTs and logout. The shared HTTP client keeps the token only in memory and attaches it without overriding multipart boundaries. An explicit Origin must exactly match the request origin, and `Sec-Fetch-Site: cross-site` is rejected. CLI clients without Origin still need a valid cookie and token. No credentialed CORS or wildcard origins are enabled.

The application requires one browser origin. An HTTPS reverse proxy must preserve the correct public Host and scheme; forwarded headers are not blindly trusted. Secure cookies must be enabled. Cross-origin frontend/API hosting is deliberately unsupported here. A stale CSRF token (for example after another tab logs in) requires a refresh; mutations are not replayed. On a logout network failure the UI retains the session and offers retry, since server logout cannot be asserted. Successful logout removes the current browser's cookie; a previously copied signed cookie cannot be individually revoked before expiry. Rotating the key invalidates all cookies. Do not use this design for real patient accounts.

## Verification

```powershell
.\backend\.venv\Scripts\python.exe -m pytest -q
.\backend\.venv\Scripts\python.exe -m pytest -q backend/tests/test_pdf_worker_startup.py
cd frontend
npm.cmd run test -- --maxWorkers=2
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
```

Backend fixtures generate ephemeral credentials, complete the real login/CSRF flow and use disposable SQLite databases. A suite-wide DBAPI guard rejects real non-SQLite connections before opening them. Configuration tests inspect PostgreSQL URLs without connecting. Existing AI tests mock the SDK or use mock HTTP transports. Feature component tests explicitly seed a verified fictional session; auth tests start with an empty query cache and exercise mocked HTTP bootstrap, login, expiry and logout without replacing the auth provider. Browser verification reuses the existing Chrome DevTools approach and intercepts all API traffic with synthetic responses.

## Known limits and later hardening

This shared-account demo has no server-side per-session revocation store, login throttling, account recovery, MFA, role separation or identity auditing. Do not expose it publicly without evaluating abuse protection, persistent revocable sessions, TLS/proxy/host validation, monitoring, security headers/CSP, secret rotation/storage, concurrency and accessibility review. Those are later security/deployment decisions, not implemented Step 6.2 or Step 6.3 work. Gemini project quota and live provider behavior remain unverified; no live Gemini requests are authorized.

Reference: [Flask security considerations](https://flask.palletsprojects.com/en/stable/web-security/) and [Flask session configuration](https://flask.palletsprojects.com/en/stable/config/).
